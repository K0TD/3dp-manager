# 3DP-MANAGER · K0TD fork

Утилита для автогенерации инбаундов к панели [3x-ui](https://github.com/MHSanaei/3x-ui), формирования единых подписок, управления несколькими 3x-ui нодами и настройки relay-перенаправления трафика. Этот форк развивает исходный проект [DenPiligrim/3dp-manager](https://github.com/denpiligrim/3dp-manager) и распространяется на тех же условиях GPL-3.0.

## Описание

Главная цель утилиты — сделать так, чтобы ваш трафик не выглядел одинаковым. 3DP-MANAGER генерирует по заданному интервалу набор подключений с разными параметрами:

- протоколы: `vless`, `vmess`, `shadowsocks`, `hysteria2`, `trojan`;
- порты: `443`, `8443` (фиксированные) и случайные из диапазона `10000-59999`;
- транспорт: `tcp`, `websocket`, `grpc`, `xhttp`;
- SNI берутся из белого списка доменов (whitelist) или задаются вручную;
- нода, relay-сервер, порт и флаг могут настраиваться отдельно для каждого инбаунда.

Все подключения объединяются в одну подписку со статичным URL. 3DP-MANAGER работает с панелью `3x-ui` и не вмешивается в её работу напрямую, используя открытое API панели.

Вторичная цель — стабильность подключения: клиент получает несколько вариантов подключений и может выбрать любой из них. В одну подписку можно добавлять инбаунды с разных нод, использовать relay-серверы и добавлять собственные внешние ссылки как кастомные подключения.

Дополнительно: 3DP-MANAGER можно использовать в каскадной схеме. Сервис перенаправления автоматически настроит переадресацию подписки и трафика к выбранной ноде.

Рекомендации:

- Используйте HTTPS для подписки (домен + SSL сертификат).
- Интервал генерации задавайте ≥ 10 минут; для стабильности рекомендуется — раз в сутки (1440 минут).
- В клиенте установите автообновление чаще (например, каждый час), чтобы была синхронизация с сервером.

## Возможности

- Генерация разнообразных подключений для одной или нескольких подписок
- Формирование единой подписки со статичным URL
- Управление несколькими нодами `3x-ui`
- Авторизация нод по логину/паролю или токену
- Автоопределение IP, страны и флага ноды по URL панели
- Выбор ноды, relay-сервера, флага, SNI и порта для каждого инбаунда
- Поддержка фиксированного порта или значения `random`
- Кастомные подключения: можно добавить готовую внешнюю ссылку в подписку
- Отдельные пути к `fullchain.pem` и `privkey.pem` для Hysteria2 UDP
- Поддержка кастомного `whitelist` доменов
- Автоматическая настройка relay-перенаправления трафика (опционально)
- Установка Web UI через HTTP или HTTPS: Let's Encrypt, self-signed или свои сертификаты
- Совместимость с cookie/CSRF и token API `3x-ui` 2.9.4–3.x
- Независимая ротация по нодам: сбой одной ноды не блокирует остальные
- Сохранение последнего рабочего поколения до успешной замены
- Фоновая очистка старых поколений после восстановления недоступной ноды
- Безопасное, отложенное и принудительное удаление нод
- Постоянные подключения AmneziaWG, WireGuard и HTTP/SOCKS/mixed; MTProto FakeTLS
- SNI-профили с fingerprint и настройками Reality/XHTTP
- Клиентские профили Happ/INCY, метаданные подписки и VLESS XHTTP GET через серверный API
- Полный переносимый архив подписок, UUID, настроек, нод и relay-реквизитов

## Требования

- Ubuntu 20.04 (и выше), Debian 12.11 (и выше)
- Панель `3x-ui` v2.9.4 (и выше)
- Root-доступ на сервере
- Docker и Docker Compose; если их нет, установочный скрипт попробует установить их автоматически
- Домен + SSL сертификат (опционально)

## Установка

У вас должна быть установлена панель управления `3x-ui`, которую можно поставить командой: `bash <(curl -Ls https://raw.githubusercontent.com/mhsanaei/3x-ui/master/install.sh)`

Установите проект на сервер командой:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/k0td/3dp-manager/main/install.sh)
```

Во время установки скрипт:

- проверит ОС, root-доступ, Docker и Docker Compose;
- при нехватке RAM создаст swap-файл 2 GB, если swap отсутствует;
- предложит выбрать режим доступа к Web UI:
  - HTTPS через Let's Encrypt;
  - HTTPS с self-signed сертификатом;
  - HTTPS со своими сертификатами;
  - HTTP без шифрования;
- сгенерирует случайный порт Web UI;
- сгенерирует логин и пароль администратора;
- развернёт контейнеры `postgres`, `backend` и `frontend`.

После завершения установки в терминале будут показаны URL, логин и пароль. Сразу смените пароль в настройках 3DP-MANAGER.

<sup>Краткое описание: запускает интерактивный скрипт установки, подготавливает окружение и разворачивает контейнеры проекта.</sup>

## Обновление

Обновление до последней версии:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/k0td/3dp-manager/main/install.sh)
```

Та же команда обнаруживает существующую установку, включая установку из репозитория `denpiligrim`, создаёт резервную копию PostgreSQL, переключает образы на K0TD и применяет миграции без удаления Docker volume.

## Перенос панели

1. На старом сервере откройте **Настройки → Перенос панели**, введите текущий пароль администратора и скачайте `.3dp-backup`. Архив можно защитить отдельной парольной фразой.
2. Скопируйте архив на новый сервер.
3. Запустите установку с восстановлением:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/k0td/3dp-manager/main/install.sh) --restore /root/panel.3dp-backup
```

Установщик заново спросит режим HTTP/HTTPS и адрес Web UI. UUID подписок, настройки, ноды и relay-реквизиты сохраняются. Для зашифрованного архива установщик запросит парольную фразу.

## Удаление

Полное удаление сервиса:


<sup>Краткое описание: удаляет контейнеры и файлы конфигурации, возвращая систему к состоянию до установки.</sup>

## Ноды

Раздел **Ноды** позволяет подключить одну или несколько панелей `3x-ui`.

Для каждой ноды указываются:

- название;
- URL панели `3x-ui`;
- IP ноды;
- флаг/страна;
- тип авторизации: `password` или `token`;
- признак основной ноды;
- разрешение self-signed TLS, по умолчанию выключенное.

После ввода URL приложение пытается определить IP и страну ноды автоматически. Флаг используется в названиях подключений внутри подписки, чтобы в клиенте было проще отличать серверы.

> [!NOTE]
> Основная нода используется как значение по умолчанию для подписок, инбаундов и relay-серверов.

Статус и время ответа каждой ноды обновляются в фоне. Доступны три режима удаления:

- `safe` (по умолчанию): сначала удаляет inbound на 3x-ui; при ошибке удаление ноды прерывается, но уже удалённые в панели inbound не восстанавливаются.
- `deferred`: сразу скрывает ноду и помечает её inbound для фоновой очистки.
- `force`: удаляет ноду и её inbound из базы без обращения к 3x-ui. Оставшиеся в панели подключения потребуется удалить вручную.

Подписки сохраняются; ссылки на удалённую ноду и связанные с ней relay убираются из конфигураций и стандартных inbound. В режимах `deferred` и `force` затронутые конфигурации отключаются и могут автоматически включиться при следующей ротации, если доступна подходящая нода. При удалении последней ноды для новых подключений потребуется добавить другую.

Шестерёнка в строке ноды открывает **Быстрые настройки → Маршрутизация**. Три независимых переключателя блокируют российские домены/IP, сервисы определения IP и направляют Google через IPv4. Блокировки используют существующий выход `blocked` (`blackhole`), а Google — выход `IPv4` (`freedom`, стратегия `UseIPv4` или `ForceIPv4`). При отсутствии совместимого выхода соответствующий переключатель недоступен. Изменения отправляются в выбранную 3x-ui только по кнопке **Применить**; проверяются сохранённые настройки и работа Xray. Применение может кратко прервать подключения.

Переключатель **Google через IPv4** управляет правилом `geosite:google → IPv4`, включая уже существующее простое правило без дополнительных условий. Выключение удаляет его, повторное включение восстанавливает без дубликатов. DNS-серверы и настройки существующих выходов не меняются. Прежние правила блокировки менеджера переводятся на `blocked` при следующем применении; старый выход `3dp:…:block` удаляется только если он создан менеджером, не изменён и больше нигде не используется.

Блокировка действует на сервере: выбранные сайты перестают открываться через ноду. Клиентский обход VPN не настраивается. Российский набор использует зоны `.ru`, `.su`, `.рф`, `geosite:category-ru` и `geoip:ru`; необходимые геобазы должны быть установлены в панели. Приложение не скачивает их автоматически. Охват зависит от геобаз и видимости домена (например, ECH может скрывать его); трафик протоколов, обходящих Xray, не покрывается.

На поддерживаемых inbound включается распознавание доменов только для маршрутизации. Новые подключения, создаваемые менеджером при генерации и ротации, наследуют эти настройки. Для inbound, добавленных вручную в 3x-ui, повторно нажмите **Применить** после обновления состояния. При отключении пресетов удаляются управляемые ими правила и восстанавливаются изменённые приложением поля; последующие ручные изменения сохраняются либо показываются как конфликт.

При ошибке приложение пытается вернуть прежние настройки. Если ответ панели потерян или откат не подтверждён, окно показывает это явно; генерация новых inbound временно приостанавливается для этой ноды. Проверьте 3x-ui, нажмите **Обновить состояние**, затем повторно **Применить**. Недоступный API или неподдерживаемая авторизация отображаются в окне настроек. Служебные данные восстановления хранятся в БД менеджера; миграция добавляется при обычном запуске с включёнными миграциями.

## Настройка

1. Добавьте ноду с адресом 3x-ui и данными авторизации. Основная нода используется по умолчанию.
2. При необходимости добавьте relay-сервер и установите на нём перенаправление.
3. Настройте список SNI-доменов в разделе **Домены**.
4. Создайте подписку, выберите подключения и сохраните её. Публичный адрес `/bus/<UUID>` остаётся прежним при ротации.

## Подписки

Раздел **Подписки** управляет статичными URL подписок и составом инбаундов.

При создании новой подписки по умолчанию добавляются: `hysteria2-udp`, `vless-xhttp-reality`, `vless-tcp-tls`, `vless-tcp-reality` и `vless-grpc-reality`.

Для каждого инбаунда можно настроить:

- тип подключения;
- ноду;
- relay-сервер;
- флаг;
- порт: конкретное число `1-65535` или `random`;
- SNI: конкретный домен или `random`;
- готовую внешнюю ссылку для типа `custom`.

Панель автоматически проверяет версии 3x-ui и Xray на каждой ноде и не даёт
выбрать несовместимый тип подключения. Версии и доступность TLS-сертификата
показываются в разделе **Ноды**.

### Типы подключений и SNI

Поддерживаются VLESS TCP/XHTTP/gRPC с Reality, VLESS WS без TLS, VLESS TCP/WS/XHTTP с TLS, VMess TCP, Shadowsocks TCP, Trojan TCP Reality, Hysteria2 UDP, MTProto FakeTLS, AmneziaWG, WireGuard, HTTP, SOCKS, mixed и внешние ссылки `custom`. Доступность зависит от версий 3x-ui и Xray на ноде.

Для VLESS/Trojan Reality встроенные SNI-профили по домену выбирают fingerprint и связанные параметры `spiderX`, пути и padding XHTTP; при отсутствии совпадения используется fallback с fingerprint `chrome`. SNI выбирается явно или как `random` из списка доменов. Эти профили описывают параметры подключения и не являются серверными пресетами маршрутизации.

В форме подписки можно выбрать `vless-xhttp-get`: XHTTP `packet-up`, uplink GET, без TLS и без SNI. Он может использовать relay; дополнительные параметры XHTTP передаются в ссылке через `extra`.

Доступны варианты VLESS с обычным TLS:

- `vless-tcp-tls` — TCP + TLS с flow `xtls-rprx-vision`;
- `vless-ws-tls` — WebSocket + TLS с путём `/` и TLS-именем ноды;
- `vless-xhttp-tls` — xHTTP + TLS с путём `/`, режимом `auto` и без Vision flow. Выбирается отдельно в редакторе; стандартный набор новой подписки не меняется.

Для `hysteria2-udp`, `vless-tcp-tls`, `vless-ws-tls` и `vless-xhttp-tls` доступны два режима:

- **Сертификат ноды** — пути запрашиваются у выбранной 3x-ui через
  `getWebCertFiles`; если панель их не возвращает, inbound не создаётся и
  действующее поколение сохраняется;
- **Свой сертификат** — задаются TLS server name и оба абсолютных пути
  `certificateFile`/`keyFile` на выбранной ноде.

SNI Reality и домены маскировки не используются для построения путей к TLS-файлам.

`amneziawg` доступен для ручного выбора при создании подписки и генерирует клиентскую ссылку `vpn://` с конфигурацией AmneziaWG 3.1. Для него требуется 3x-ui 3.7 или новее; в стандартный набор новой подписки он не входит.

`wireguard`, `amneziawg`, `mixed`, `http` и `socks` создаются при сохранении подписки, даже если авторотация выключена. Они сохраняют ключи, пароль и порт при автоматической и ручной ротации. Название, флаг и порядок можно менять без пересоздания. Чтобы изменить порт, ноду, тип либо relay: удалите инбаунд, сохраните подписку, откройте редактор, добавьте подключение заново и снова сохраните. Допускается удаление единственного инбаунда с сохранением пустой подписки. Удалённое подключение сразу исчезает из выдачи подписки; очистка на панели выполняется фоновой очередью.

Для обычного WireGuard страница подписки выдаёт `.conf` и QR-код: MTU 1360, PersistentKeepalive 25, отдельные ключи сервера и клиента, preshared key, маршруты IPv4/IPv6. Для AmneziaWG MTU учитывает дополнительное заполнение пакетов. Для HTTP/SOCKS/mixed показываются адрес, порт, логин и пароль; внутренние URI этих подключений не добавляются в обычную base64-подписку. На современных панелях SOCKS создаётся как `mixed`, поскольку API не принимает отдельный протокол `socks`; этот слушатель также принимает HTTP. UDP для HTTP/SOCKS/mixed выключен.

`mtproto-faketls` использует встроенный MTProto панели с `routeThroughXray: true`. Создание отклоняется, если панель не выделила `routeXrayPort`. Это не установка отдельного сервиса Telemt. Для всех протоколов применяются существующие правила маршрутизации Xray; направление в mihomo должно быть настроено на самой ноде.

Перед созданием менеджер проверяет состояние Xray и получает TLS-пути с выбранной ноды. В режиме `node` остаточные пользовательские пути и SNI игнорируются. Проверяется соответствие домена в известных каталогах сертификатов TLS-имени; после сохранения проверяется, что панель не подменила TLS-имя и пути. Проверка каталога не заменяет проверку SAN, срока действия и наличия файлов на сервере. Неисправный существующий инбаунд не исправляется автоматически. На главной странице ошибки операций показываются понятным текстом с подсказкой; технические детали доступны в свёрнутом блоке. Диагностика включает этап, конфигурацию и, если известен, блокирующий инбаунд; секреты из технического сообщения удаляются.

### Профили маршрутизации и метаданные

В форме подписки выберите тип **Happ routing** или **INCY routing** и укажите профиль в многострочном поле. В API им соответствуют элементы `happ-routing` и `incy-routing` в `inboundsConfig` с полем `routingProfile`. Happ принимает JSON-объект, его base64 или `happ://routing/add|onadd|off`; INCY также принимает HTTP(S)-ссылку на профиль и `incy://routing`/`incy://autorouting`. В прямой и relay-выдаче включённые строки профилей идут перед ссылками подключений. Это клиентские правила: они не создают inbound на панели и не входят в лимит 20 подключений.

В форме подписки можно задать **примечание**, **ссылку поддержки** и **сайт**. В API им соответствуют `note` (до 200 символов), `supportUrl` (HTTP/HTTPS/TG) и `websiteUrl` (HTTP/HTTPS). Выдача передаёт их в заголовках `announce`, `support-url` и `profile-web-page-url`, а имя — в `profile-title`. Подробнее — в [api.md](api.md).

Обычное удаление подписки прерывается, если панель не удалила inbound. При принудительном удалении (`force=true`) подписка удаляется и в случае ошибки панели; оставшиеся inbound нужно проверить и при необходимости удалить в 3x-ui вручную.

Если панель отклонила создание постоянного подключения, интерфейс сообщает об ошибке отдельно от сохранения настроек. После восстановления панели повторите сохранение: уже созданные подключения не дублируются.

Стрелки рядом с номером инбаунда меняют порядок ссылок. Новый порядок применяется к активной подписке сразу после сохранения и сохраняется при последующих ротациях.

Если порт или SNI указаны как `random`, значение будет выбрано при ротации из доступного диапазона или whitelist доменов. Для постоянных подключений случайный порт выбирается однократно при создании.

## Установка сервиса перенаправления (forwarding)

> [!WARNING]  
> Сервис перенаправления работает на промежуточном сервере

Сервис перенаправления позволяет проксировать входящие порты с промежуточного сервера на выбранную ноду. В Web UI такие серверы настраиваются в разделе **Relay серверы** и могут быть привязаны к конкретной ноде.

Relay-сервер можно добавить по IP или домену. Если указан домен, backend попытается определить IP автоматически.

Для ручной установки forwarding на промежуточном сервере замените `IP_ADDRESS` на IP основной ноды:

```bash
sudo ORIGIN_IP="IP_ADDRESS" bash -c "$(curl -sSL https://raw.githubusercontent.com/k0td/3dp-manager/main/forwarding_install.sh)"
```

<sup>Краткое описание: добавляет правила перенаправления.</sup>

## Удаление перенаправления

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/k0td/3dp-manager/main/forwarding_delete.sh)
```

<sup>Краткое описание: удаляет правила перенаправления. После удаления, чтобы изменения вступили в силу, перезапустите фаервол `ufw reload` и перезапустите систему `reboot`</sup>

## Сбор доменов из мульти-подписок

Утилита извлекает домены из подписок и формирует `whitelist` для генератора.

```bash
node get_domains.js
```

<sup>Краткое описание: добавьте ссылку на мульти-подписку в скрипт и запустите команду — на выходе получите список доменов. Необходим `Node.js` для работы скрипта.</sup>

## Замечания и текущие ограничения

- Общий список доменов работает не у всех провайдеров, поэтому рекомендуется составить и использовать свой whitelist.
